# **Детальная техническая спецификация v3.0: Система асинхронной генерации контента Gemini Media MCP**

**Дата разработки:** 27 ноября 2025 г.  
**Версия:** 3.0 (с учётом результатов исследования Batch API)

---

## **1\. Введение и Глоссарий**

### **1.1. Стратегическая цель и Обоснование**

Данный проект направлен на фундаментальную трансформацию архитектуры текущего MCP-сервера. Из синхронного инструмента типа "запрос-ответ", который блокирует работу агента и зависит от стабильности соединения, мы переходим к надежной асинхронной системе управления задачами.

**Главные цели внедрения:**

1. **Финансовая эффективность:** Использование Google Batch API для генерации изображений позволяет получить скидку в 50%. ⚠️ **ВАЖНО:** После детального исследования (27.11.2025) установлено, что **TTS Batch API документирован, но не работает на практике** (баг подтверждён форумом Google). Для TTS используется локальная очередь с rate limiting.
2. **Архитектурная надежность (Fault Tolerance):** Система должна быть устойчива к "исчезновению" клиента. Если пользователь закрыл ноутбук, интернет пропал или процесс агента упал — задача не должна потеряться. Результат должен быть получен и сохранен при следующем запуске.  
3. **Прозрачность (Observability):** AI-агент должен иметь возможность в любой момент узнать, на какой стадии находится длительная задача, не гадая и не видя ошибок тайм-аута.  
4. **Нулевая конфигурация (Zero Config):** Развертывание должно происходить "из коробки", без необходимости поднимать Docker-контейнеры с Redis или PostgreSQL.

### **1.2. Расширенный Глоссарий**

* **Task (Задача):** Атомарная единица работы. Это может быть генерация одной картинки по одному промпту или синтез одного аудио-фрагмента. Каждая задача имеет свой уникальный жизненный цикл и статус.  
* **Batch (Пакет):** Логическая группировка задач, созданная пользователем в один момент времени. Пакет позволяет управлять множеством задач как единым целым (например, "Генерация иллюстраций для Главы 1").  
* **Inline Request:** Метод передачи данных в Google Batch API, при котором полезная нагрузка (JSON) отправляется непосредственно в теле HTTP-запроса. Это избавляет от необходимости использовать Google Cloud Storage для промежуточного хранения, но накладывает лимит в 20 МБ на размер пакета, что вполне достаточно для текстовых промптов.  
* **Background Worker (Фоновый Воркер):** Автономный поток исполнения, который берет на себя всю "грязную работу": общение с внешним API, ожидание, скачивание файлов и обработку ошибок.  
* **Payload (Полезная нагрузка):** Полный набор данных, необходимых для воспроизведения задачи (сериализованные параметры запроса).

## **2\. Архитектура и Жизненный Цикл**

### **2.1. Компоненты системы и их взаимодействие**

1. **Server Process (Main Thread / FastMCP):**  
   * Это "лицо" системы. Он слушает запросы от MCP-клиента (Claude/Cline).  
   * Его задача — **не блокироваться**. Он должен принять параметры, валидировать их, быстро записать задачу в БД и вернуть Агенту "квитанцию" (Task ID).  
   * Он *никогда* не вызывает долгие методы Google API напрямую.  
2. **Database Layer (SQLite Persistence):**  
   * Файл gemini\_tasks.db — это "мозг" системы.  
   * Используется встроенная библиотека sqlite3.  
   * Обеспечивает ACID-транзакции. Это гарантирует, что если питание отключится в момент записи, база не повредится.  
   * Служит единственным каналом коммуникации между Сервером и Воркером.  
3. **Background Worker (Daemon Thread):**  
   * Запускается параллельно с основным сервером.  
   * Работает в бесконечном цикле с интервалом ("тик") в 30–60 секунд.  
   * Реализует паттерн "State Machine" (Конечный автомат), переводя задачи из статуса в статус (PENDING \-\> SUBMITTED \-\> COMPLETED).  
4. **Notification System (UX Layer):**  
   * Отвечает за "последнюю милю" — информирование человека.  
   * Использует нативные средства ОС (PowerShell для Windows, AppleScript для macOS) для показа всплывающих уведомлений (Toasts), когда пакет задач полностью готов.

**Ключевые термины (Glossary):**

* **Inline Requests** — метод передачи данных в Batch API непосредственно в JSON-теле запроса (альтернатива — хранение в BigQuery).
* **Graceful Shutdown** — корректное завершение фонового потока при остановке сервера (ожидание завершения текущих задач или их сохранение).
* **Execution Mode (Режим выполнения)** — способ обработки операции: `batch` (через Google Batch API с 50% скидкой) или `local_queue` (последовательное выполнение с rate limiting без скидки).

### **2.2. Детальный механизм Инициализации (Startup Sequence)**

При запуске файла server.py происходит следующая цепочка событий:

1. **Bootstrap:** Загружаются переменные окружения и конфиги.  
2. **DB Check:** Вызывается DatabaseManager.initialize().  
   * Проверяется наличие файла БД.  
   * Если файла нет — создается структура таблиц (CREATE TABLE IF NOT EXISTS).  
   * Проверяется наличие базовых данных в справочниках (seed data).  
3. **Worker Spawn:** Вызывается WorkerManager.start().  
   * Создается объект потока threading.Thread(target=worker\_loop, daemon=True). Флаг daemon=True критически важен: он позволяет операционной системе корректно убить этот поток, когда основной процесс сервера завершается, не оставляя процессов-зомби.  
   * Воркер делает первый "пробный" проход (Health Check), проверяя, не осталось ли "зависших" задач с прошлого запуска (статус PROCESSING). Если такие есть — они немедленно ставятся в очередь на проверку.

## **3\. Схема Базы Данных (Database Schema)**

База данных спроектирована с учетом 3-й нормальной формы для обеспечения целостности данных.

### **3.1. Таблица справочник: operation\_types**

Эта таблица необходима для жесткой типизации и будущей аналитики расходов.

CREATE TABLE operation_types (
    operation_type TEXT PRIMARY KEY,  -- например: 'IMG_GEN', 'TTS_GEN'
    display_name TEXT,                -- "Генерация изображения"
    description TEXT,                 -- краткое описание
    execution_mode TEXT NOT NULL,     -- 'batch' (Google Batch API) или 'local_queue' (последовательная обработка)
    default_priority INTEGER DEFAULT 5,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- Seed данные с учетом результатов исследования:
-- IMG_GEN: batch mode ✅ (Batch API работает, 50% скидка)
-- TTS_GEN: local_queue mode ⚠️ (Batch API документирован, но возвращает 404 NOT_FOUND)

### **3.2. Таблица: batches (Очереди)**

Представляет собой "контейнер" для группы задач.

| Поле | Тип | Ограничения | Описание |
| :---- | :---- | :---- | :---- |
| id | TEXT | PK (UUID) | Локальный GUID пакета. Генерируется на клиенте. |
| google\_batch\_id | TEXT | NULLABLE, INDEX | ID, присвоенный Google Cloud. Нужен для поллинга статуса через API. |
| created\_at | DATETIME | NOT NULL | Метка времени создания. |
| completed\_at | DATETIME | NULLABLE | Метка времени завершения последней задачи. |
| status | TEXT | DEFAULT 'PENDING' | Агрегированный статус. Важно: статус батча считается COMPLETED только когда ВСЕ задачи внутри имеют терминальный статус. |
| total\_tasks | INTEGER | DEFAULT 0 | Счетчик задач для быстрого отображения прогресса (например, "3 из 10"). |

### **3.3. Таблица: tasks (Единичные Задачи)**

Основная таблица, хранящая историю и состояние каждого файла.

| Поле | Тип | Ограничения | Описание |
| :---- | :---- | :---- | :---- |
| id | TEXT | PK (UUID) | Уникальный ID задачи. |
| batch\_id | TEXT | FK \-\> batches.id | Ссылка на родительский пакет. |
| operation\_code | TEXT | FK \-\> operation\_types | Тип выполняемой работы. |
| status | TEXT | DEFAULT 'PENDING' | PENDING (Ждет отправки), SUBMITTED (В облаке), PROCESSING (Обрабатывается), COMPLETED (Успех), FAILED (Ошибка генерации), DELIVERY\_FAILED (Файл есть, но сохранить не удалось). |
| input\_payload | TEXT | NOT NULL (JSON) | **Критически важное поле.** Содержит дамп всех аргументов функции: { "prompt": "...", "voice": "Kore", "model": "gemini-2.5" }. Позволяет реализовать кнопку "Retry" без участия пользователя. |
| search\_keywords | TEXT | NULLABLE | Денормализованное поле для полнотекстового поиска (FTS). Сюда при создании копируются ключевые слова из промпта. |
| target\_path | TEXT | NOT NULL | Путь назначения, указанный пользователем. |
| local\_path | TEXT | NULLABLE | Реальный путь, куда файл был сохранен (может отличаться от target\_path в случае конфликтов имен или ошибок доступа). |
| error\_details | TEXT | NULLABLE | Полный стек-трейс или сообщение об ошибке от Google API. |
| created\_at | DATETIME | DEFAULT CURRENT\_TIMESTAMP | Время создания. |
| updated\_at | DATETIME | DEFAULT CURRENT\_TIMESTAMP | Время последнего изменения статуса (Heartbeat). |
| completed\_at | DATETIME | NULLABLE | Финальная временная метка. Используется для расчета метрик скорости. |

## **4\. Детальные Алгоритмы работы (Logic Flow)**

### **4.1. Сценарий: Постановка задачи (Tools Layer \-\> DB)**

Этот процесс должен занимать миллисекунды.

1. **Прием:** Инструмент (например, queue\_audio\_generation) получает запрос от Агента.  
2. **Валидация:** Проверяются входные параметры (существует ли модель, валиден ли YAML).  
3. **Подготовка:**  
   * Генерируется UUID для batch\_id.  
   * Входные данные сериализуются в JSON для поля input\_payload.  
4. **Транзакция БД (Atomic):**  
   * BEGIN TRANSACTION  
   * INSERT в batches.  
   * INSERT в tasks (одна или несколько записей) со статусом PENDING.  
   * COMMIT  
5. **Ответ:** Агенту немедленно возвращается текстовый ответ: *"Пакет задач \[UUID\] успешно сформирован и поставлен в очередь. Я работаю в фоне."*

### **4.2. Сценарий: Фоновый Воркер (Worker Loop)**

Воркер — это бесконечный цикл, который спит большую часть времени, но просыпается для проверки состояния.  
**Фаза 1: Отправка (Submission Phase)**

1. Воркер делает выборку: SELECT \* FROM tasks WHERE status \= 'PENDING' LIMIT 100\.  
2. Группировка: Задачи группируются по batch\_id.  
3. Для каждого пакета:  
   * Формируется BatchGenerateContentRequest. Используется метод **Inline**, так как мы передаем только текстовые JSON-объекты.  
   * Выполняется вызов API: client.batches.create(...).  
   * Полученный от Google resource\_name (например, batches/12345) сохраняется в таблицу batches в поле google\_batch\_id.  
   * Статусы задач и батча обновляются на SUBMITTED или PROCESSING.

**Фаза 2: Мониторинг и Получение (Polling & Retrieval Phase)**

1. Воркер выбирает активные батчи: SELECT \* FROM batches WHERE status IN ('SUBMITTED', 'PROCESSING').  
2. Для каждого батча:  
   * Делается легкий запрос client.batches.get(name=google\_batch\_id).  
   * Если статус JOB\_STATE\_RUNNING или PENDING — пропускаем, ждем следующего цикла.  
   * Если статус JOB\_STATE\_SUCCEEDED:  
     * Запускается процедура скачивания результатов (Download). Результат — это JSONL файл, где каждая строка — это ответ на конкретную задачу.  
     * **Матчинг:** Воркер сопоставляет ответы из файла с задачами в БД (используя custom\_id, который мы передаем при создании задачи).  
     * **Обработка контента:**  
       * Декодирование Base64 \-\> Бинарные данные (WAV/PNG).  
       * **Безопасное сохранение:**  
         * Проверка доступности директории из target\_path.  
         * Если директория доступна: Сохранение файла. Статус \-\> COMPLETED.  
         * Если директория недоступна/удалена: Создание резервной папки output/lost\_and\_found/{YYYY-MM-DD}/. Сохранение туда. Статус \-\> DELIVERY\_FAILED. Поле error\_details обновляется сообщением: *"Target directory lost, saved to fallback"*.  
   * Если статус JOB\_STATE\_FAILED:  
     * Все задачи пакета переводятся в статус FAILED. Ошибка записывается в error\_details.

**Фаза 3: Завершение (Completion Phase)**

1. Если все задачи в пакете имеют терминальный статус, обновляем статус пакета batches на COMPLETED.  
2. Инициируем системное уведомление.

## **5\. Спецификация Инструментов (API для Агента)**

Эти функции регистрируются в MCP и доступны Клоду/Клайну.

### **5.1. Генерация (Creation Tools)**

* **queue\_audio\_generation(script\_yaml: str, output\_dir: str, model: str)**  
  * Принимает YAML сценарий. Разбирает его на реплики.  
  * Создает один Batch, в котором каждая реплика — отдельная Task.  
* **queue\_image\_generation(prompts: List\[str\], output\_dir: str, model: str, aspect\_ratio: str)**  
  * Специально принимает *список* промптов.  
  * Идеально для создания вариаций. Создает Batch с множеством Task.

### **5.2. Мониторинг и Контроль (Management Tools)**

* **check\_task\_status(task\_id: str)**  
  * Возвращает подробный статус конкретной задачи.  
* **check\_batch\_status(batch\_id: str)**  
  * Возвращает сводку: *"Пакет \[ID\]: 5 задач выполнено, 2 в процессе. Успешные файлы: \[список путей\]"*.  
  * Если есть ошибки DELIVERY\_FAILED, явно указывает на них и путь к lost\_and\_found.  
* **get\_pending\_work()**  
  * Диагностический инструмент. Показывает Агенту, чем сейчас занят сервер ("В очереди 5 пакетов, 150 задач").

### **5.3. Поиск и История (Discovery Tools)**

* **search\_history(query: str, operation\_type: Optional\[str\], limit: int \= 10\)**  
  * Мощный инструмент контекстной памяти.  
  * Выполняет SQL LIKE поиск по полю search\_keywords и input\_payload.  
  * Позволяет отвечать на запросы: *"Мы неделю назад делали картинку с киберпанк-городом, найди её"* или *"Покажи все аудио, сгенерированные голосом Kore"*.

## **7\. Поэтапный План Внедрения (Implementation Roadmap)**

### **Фаза 0: Валидация Batch API (Validation Phase)** ⚠️ **КРИТИЧНО**

**Цель:** Экспериментальная проверка работоспособности Google Batch API для всех планируемых типов операций перед началом разработки.

**Задача 0.1:** Создать тестовый скрипт `scripts/check_batch_api.py` с 4 сценариями:

1. **Text-to-Text (базовый тест):**

   ```python
   inline_requests = [{'contents': [{'parts': [{'text': 'Hello, world'}]}]}]
   batch_job = client.batches.create(model='gemini-2.5-flash', src=inline_requests)
   ```

   **Ожидаемый результат:** ✅ SUCCESS (базовая функциональность Batch API)

2. **Text-to-Image (gemini-2.5-flash-image):**

   ```python
   inline_requests = [{
       'contents': [{'parts': [{'text': 'A cat in space'}]}],
       'config': {'response_modalities': ['TEXT', 'IMAGE']}
   }]
   batch_job = client.batches.create(model='gemini-2.5-flash-image', src=inline_requests)
   ```

   **Ожидаемый результат:** ✅ SUCCESS (документация подтверждает, официальные примеры работают)

3. **Image-to-Image editing (reference image + prompt):**

   ```python
   inline_requests = [{
       'contents': [{
           'parts': [
               {'inline_data': {'mime_type': 'image/jpeg', 'data': base64_image}},
               {'text': 'Add a wizard hat to this cat'}
           ]
       }],
       'config': {'response_modalities': ['IMAGE']}
   }]
   batch_job = client.batches.create(model='gemini-3-pro-image-preview', src=inline_requests)
   ```

   **Ожидаемый результат:** ✅ SUCCESS (поддерживается согласно документации)

4. **Text-to-Audio TTS (gemini-2.5-flash-preview-tts):**

   ```python
   inline_requests = [{
       'contents': [{'parts': [{'text': 'Hello from Gemini TTS'}]}],
       'config': {
           'speech_config': {'voice_config': {'prebuilt_voice_config': {'voice_name': 'Kore'}}}
       }
   }]
   batch_job = client.batches.create(model='gemini-2.5-flash-preview-tts', src=inline_requests)
   ```

   **Ожидаемый результат:** ❌ 404 NOT_FOUND с сообщением `"not supported for batchGenerateContent"` (баг в Google API, подтвержден форумом discuss.ai.google.dev/t/104621)

**Задача 0.3:** На основе результатов финализировать execution_mode для каждого operation_type:

* Если Batch работает → `execution_mode='batch'` (50% скидка)
* Если Batch не работает → `execution_mode='local_queue'` (обычная цена, последовательная обработка с rate limiting)

**Критерий готовности:** Четкое понимание, какие операции получат скидку 50%, а какие — нет. Обновленная таблица operation_types с корректными execution_mode.
